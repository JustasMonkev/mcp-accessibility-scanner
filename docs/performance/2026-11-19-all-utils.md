## Every direct function and method

Times are microseconds per call. Each value is the median of three fresh-process medians. Each process warms up four batches and records twelve batches per revision, alternating their order and using the same batch size for both. Inputs and mutable fixtures are prepared outside the timed window. Timer, browser and I/O rows include the work explicitly described in their module. Ratios below 1 indicate a slower candidate measurement. Small differences near the harness controls can move between runs. Full per-process samples are available in the JSON.

The 100-URL selection fixture fell from 858 µs to 544 µs. The default browser completion path took about 603 ms on both builds, including its configured waits. Attaching through CDP took 19.9 ms on the baseline and 21.2 ms on the candidate.

Both revisions must agree on checked outputs. Checks project internal representations to comparable fields and validate formats for randomized output. The inventory parses the compiled code and rejects a missing direct fixture. Private declarations are accessible only to the benchmark loader.

## Nested callbacks

A separate replay instruments callback bodies and records inclusive elapsed time. This keeps instrumentation out of the direct benchmarks. For a callback returning a promise, the timer ends when its body returns unless the body explicitly awaits work. Tiny callback timings include clock overhead. A single observation establishes execution only. Five CDP callbacks per revision use injected in-process lifecycle events on real disposable connections. The HTTP fallback uses a test response object. The table identifies these rows. Other callbacks execute through the fixture workloads, setup and cleanup.

Locations are one-based line and column positions in the compiled JavaScript for that revision. Raw results include both revisions.
